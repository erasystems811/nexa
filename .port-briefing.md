## Your job, per page

For each real Nexa page file you're assigned:

1. Read the CURRENT file in this repo first. It already has the correct real data
   fetching (Supabase queries via `@/modules/*`), auth guards (`requireSession`,

   its composition/structure/visual language.
3. Rewrite the Nexa page's JSX so it matches the reference's composition, styling with

   mockup's data shape differs from Nexa's real data (it will — the mockup invented

   your judgment and stay consistent with the visual language used elsewhere (ask
   yourself "what would this reference designer have built for this real feature").

## What's already set up — use it, don't rebuild it

- **Tokens/fonts** (`src/app/globals.css`, already ported from the reference): use
  Tailwind semantic classes — `bg-background` (page bg, warm paper), `bg-card` (white
  card fill), `text-foreground`, `text-muted-foreground`, `bg-primary`/`text-primary`
  (navy — the main brand/action color), `bg-accent`/`text-accent` (terracotta — used
  SPARINGLY for standout/attention moments only, e.g. a "Featured" badge, an urgent
  stat), `bg-secondary`/`text-secondary-foreground` (warm neutral tint, section bands,
  inactive pills), `border` (default border color), `bg-destructive`/`text-destructive`
  (errors/danger). `font-serif` (Fraunces) is for headline-level moments ONLY — page
  titles, section headers, hero text. Never apply it to numbers/stats/body/labels/nav —
  those stay the default `font-sans` (Plus Jakarta Sans). Admin pages are automatically
  dark-themed (scoped via `.admin-shell` on the layout) — you don't need to do anything
  special for that, the same semantic classes just resolve to dark values there.
- **shadcn/ui primitives** (`src/components/ui/*`, already ported): Button, Card
  (+CardHeader/CardTitle/CardDescription/CardContent/CardFooter), Badge, Input, Label,
  Textarea, Select (+ sub-parts), Avatar (+Image/Fallback), Separator, Dialog (+Header/
  Footer/Title/Description/Trigger/Content), AlertDialog (full set), DropdownMenu (full
  set), Tabs (+List/Trigger/Content), Tooltip (+Trigger/Content/Provider), Skeleton,
  Progress, Popover (+Trigger/Content/Anchor), Calendar, Checkbox, RadioGroup(+Item),
  Switch. Import each from `@/components/ui/<file>` (shadcn convention, one file per
  primitive) — NOT from `@/components/ui` (that's the OLD custom system, see below).
- **`cn()` helper**: `@/lib/utils`.
- **Shell/nav**: already wired at the layout level (`src/app/layout.tsx` +
  `src/components/customer-shell.tsx` for customer, `src/app/studio/layout.tsx` for
  vendor, `src/app/admin/layout.tsx` for admin — all render through
  `src/components/shells.tsx`'s CustomerShell/VendorShell/AdminShell). **Your page does
  NOT need its own header, nav, sidebar, or outer `max-w-*`/`mx-auto`/`px-*` wrapper —
  the shell already provides `max-w-6xl mx-auto p-4 md:p-8`.** Just return the page's
  own content (a fragment, or a `<div className="space-y-8">` etc. if you need page-
  level vertical rhythm).
- **Existing shared display components** (already migrated to the new tokens, keep
  using them as-is): `VendorCard`, `ListingCard`, `StatusPill`, `SearchBar`, `Photo`,
  `CategoryIcon`, `ChatOnWhatsApp`/`PrivacyNote` (`@/components/chat-cta`),

## What's being retired — do not use

- `@/components/ui` (the OLD custom Card/Button/Badge/Field/Alert/PageHeader/StatTile/
  SectionHeader file) — don't import from it. Use the new `@/components/ui/<file>`
  shadcn primitives instead.
- `BackBar` (`@/components/back-bar`), `StudioBack` (`@/components/studio-back`),

## Sub-components

A page often imports a small co-located client component for its interactive parts
(e.g. `./booking-form`, `./order-actions`, `./add-provider`, `./bank-form`,
`./listing-form`, `./apply-form`, `./login-form`). These are presentational, not
business logic — restyle them to the new ui/* primitives too wherever they still use
the old `--color-x` token system or the old `@/components/ui`. Keep every server
action / `useActionState` / form-state call exactly as it is; only touch JSX/className.

## Pages with NO shell (skip the "no wrapper" rule for these)

`/login`, `/register`, `/reset`, `/verify`, `/apply`, `/book/[listingId]`, and
`/whatsapp/[id]` are deliberately NOT wrapped in a sidebar shell (they're focused,
full-screen flows — auth, checkout, a WhatsApp handoff). If your assigned page is one
of these, it DOES need its own centered container (e.g. `mx-auto max-w-md p-6` or
similar, matching the reference's login/register page framing) since there's no shell
providing one. Every other assigned page renders inside a shell — follow the normal
"no wrapper" rule for those.

## Guardrails

- **Never touch `src/modules/*`** — that's all real backend logic (Supabase queries,
  server actions, auth). Off-limits.
- No new npm dependencies — everything needed is already installed.
- Server components by default (matches current Next.js App Router convention already
  used in this repo). Only add `"use client"` where the current file already has it
  (interactive forms/filters), or where a shadcn primitive you're using requires it
  (Select, Dialog, Dropdown, Tabs, etc. already declare their own `"use client"` inside
  `ui/*`, so importing them from a server component page is fine — you only need `"use
  client"` on YOUR page/sub-component if you add local interactivity like `useState`).
- Keep `next/link` for navigation (never wouter — that was only the mockup's router).
- This repo uses `typedRoutes: true` — dynamic string hrefs need `href={"/x" as Route}`
  (`import type { Route } from "next"`), matching the existing pattern you'll see in the
  current files.
- After editing your assigned files, run `npx tsc --noEmit -p tsconfig.json` from
  `C:\Users\user\nexa` and fix any errors your changes introduced before finishing.
  Don't worry about pre-existing errors in files outside your assignment.
